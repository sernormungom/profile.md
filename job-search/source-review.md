## Inventory and review procedure

1. Save the original export as `job-search/inbox/bookmarks.html` (gitignored). From `job-search/`, run `python3 -I bookmark_inventory.py inbox/bookmarks.html`. Raw names, URLs and folder paths stay in gitignored `data/bookmark-inventory.json`; the ledger below contains only reviewed job-source information. The tool never opens bookmark URLs.
2. Group verified employer aliases and career URLs manually using the generated host hints and indexed employer counts. Shared ATS hosts are not employer identities. Exact URL duplicates collapse; meaningful query parameters, fragments, and every original bookmark occurrence remain. Redirect/cross-domain equivalence requires evidence.
3. Give every distinct source a disposition here; carry its bookmark names/folders as provenance. Unrelated bookmarks receive a grouped exclusion row with count, without copying private unrelated URLs. Account for every occurrence using inventory totals. Coverage is **observed**, **not observed** after an explicit check, or **unknown**. An employer name alone or absence from old search results never proves live completeness.
4. Prioritise strong embedded/controls/automotive/AI/MedTech and selective engineering-management fit with limited observed coverage. Spend 15 minutes on inventory, 30 on at most six employer groups (five minutes each; official vacancy search and up to three suitable ads), and 45 on validation/results. Stop at expensive extraction; note the next step. No new adapters in this pass.
5. Compare candidate vacancies with the saved index and a targeted public JobTech check before adding collection. Record access date, query/endpoint and representative ad IDs/URLs. A listing login blocks automatic collection without credentials; an application-only login does not. No openings today does not exclude the employer permanently.
6. If existing coverage works, add no source. Pilot a narrow missed-query candidate as a separate disabled `jobtech` source with the same `site = "platsbanken"`, existing location/direct-employment filters and no incremental watermark. Run it explicitly using `fetch --source <pilot-id> --review` (explicit selection runs disabled sources). Capture new IDs for overlap/yield review; promote only useful queries, then remove the pilot block and record the outcome. Keep stable identity and record any retained pilot provenance. New direct feeds must fit the current adapter, not merely expose some public API.
7. For additions, inspect full body/requirements, location, employer, URL, stable IDs and pagination/feed limits; fetch individually twice to verify deduplication. Existing `pages` sources require supplied ad links; they do not discover listings. Keep valuable difficult sources manual or deferred, with estimated integration effort and evidence of missed roles.
8. Run `refilter --dry-run` before applying changed filters. Inspect every proposed exclusion, especially existing deep_match/maybe results. It cannot restore historical exclusions; handle the specific recovery above separately. Screen at most 20 newly discovered ads with subscription `screen-cli`; no paid API. Spot-check promising results. Do not accidentally screen an unrelated existing backlog instead of the pilot's new ads.
